# Четыре дефекта части A: причина, исправление, доказательство

Проект продолжает ДЗ 4–5: тензоры `data/tokenized/*.pt` — выход стадии tokenize
ДЗ 4 (geo-reviews-2023, генерация отзыва по карточке организации).
Железо без ускорителя, поэтому в `params.yaml` стоят `device: cpu` и
`dtype: float32`; остальной бюджет оставлен по умолчанию — 6 конфигураций
по 4 шага, train-пул 32, val 8, batch 1 × accumulation 2.

Отпечаток всех файлов `tests/` — `c42ac7788026`, совпадает с выданным:
проверки не правились, diff прикладывать нечего.

Каждый дефект ниже воспроизведён в сломанном состоянии и замерен, а не только
описан. Для дефектов 1 и 3 сломанная версия `src/sweep.py` прогонялась в
отдельном эксперименте MLflow `hw6-lora-broken-demo` с урезанным бюджетом
(1 шаг, 2 примера) — он остался в сервере и его видно рядом с рабочим.
После замеров файлы восстановлены побайтово, контрольные суммы сверены.

## Дефект 1 — шесть конфигураций логировались в один общий run

**В чём был.** В `src/sweep.py` цикл по кандидатам был обёрнут одним общим
дочерним run:

```python
with mlflow.start_run(run_name="all-candidates", nested=True):
    for candidate in p["sweep"]:
        rows.append(run_candidate(p, candidate, versions))
```

`run_candidate` писал в `mlflow.active_run()`, то есть все шесть обучений
попадали в один и тот же run. Рядом стоял обходной приём, который и выдавал
проблему с головой: `if not mlflow.get_run(...).data.params:` — параметры
логировались только у первого кандидата, потому что у run в MLflow один набор
params и повторная запись другого значения вызвала бы ошибку.

**Как проявлялся.** Замер на сломанной версии:

```
конфигураций в params: 6
отдельных runs с kind=candidate: 1
run d9b25049: tag candidate='all-r8-high'
   params r=4 lr=0.0001 modules=q_proj,v_proj
   точек val_loss: 12
```

Один run вместо шести. Тег `candidate` равен имени **последнего** кандидата
(`set_tags` перезаписывает), а параметры в нём — от **первого** (`r=4`,
`lr=1e-4`, `q_proj,v_proj`). То есть run утверждает, что он `all-r8-high`,
а хранит гиперпараметры `qv-r4-low`. В истории метрики `val_loss` — 12 точек:
кривые шести разных моделей слиты в одну серию по шагам 0 и 1, и «лучший
кандидат» выбирался бы из перемешанных чисел.

**Как исправлен.** Один кандидат — один дочерний run; обходной `if` убран,
params пишутся всегда:

```python
for candidate in p["sweep"]:
    with mlflow.start_run(run_name=candidate["name"], nested=True):
        rows.append(run_candidate(p, candidate, versions))
```

**Каким числом подтверждается.** В рабочем эксперименте `hw6-lora`
**6 отдельных законченных runs** с уникальными run_id и собственными params;
у каждого ровно 2 точки `val_loss` (шаги 0 и 4) и 4 точки `train_loss` —
проверки 1 и 3 в `make check` требуют именно этого и проходят. Значения
`final_val_loss / base_val_loss`: 0.8909, 0.9256, 0.9365, 0.9521, 0.9700,
0.9830 — шесть различимых результатов вместо одной смеси.

## Дефект 2 — артефакты не переживали пересоздание контейнера

**В чём был.** В `compose.yaml` сервис `mlflow` запускался с
`--artifacts-destination=/mlartifacts`, но **никакого тома по этому пути не было
смонтировано**. Том `artifacts:` был объявлен в конце файла и нигде не
использовался, а на его месте стоял `# TODO: где хранятся файлы после замены
контейнера?`. Файлы писались в слой контейнера.

**Как проявлялся.** Метаданные run лежат в Postgres (у него том был), а файлы —
внутри контейнера. Пока контейнер жив, всё работает; `docker compose up
--force-recreate` создаёт новый контейнер с пустым `/mlartifacts`, и ссылки в
базе начинают указывать в никуда.

Замер на сломанной версии: probe-файл залогирован, том снят, контейнер
пересоздан, скачивание того же артефакта —

```
ПОТЕРЯН: MlflowException The following failures occurred while downloading
one or more artifacts from http://127.0.0.1:5006/api/2.0/mlflow-artifacts/...
```

Run в UI при этом остаётся на месте и выглядит исправным.

**Как исправлен.** Том подключён к сервису:

```yaml
    volumes:
      - artifacts:/mlartifacts
```

**Каким числом подтверждается.** После исправления та же последовательность
(залогировать probe → `up --force-recreate --wait mlflow` → скачать) возвращает
файл с совпадающим SHA256: `45ed94865f5f3730a3fe804495c97e921b952b6e2687…`.
`make check-storage` печатает «PASS: новый контейнер вернул тот же артефакт»,
проверка 8 сверяет `compose_sha256` и хеш файла и проходит. Симметрия полная:
без тома тот же самый артефакт теряется, с томом возвращается байт в байт.

## Дефект 3 — у runs не было версий train и val

**В чём был.** В `src/sweep.py` хеши данных вырезались из provenance ровно
перед тем, как превратиться в теги:

```python
versions = {k: v for k, v in provenance(p).items() if not k.startswith("data_")}
```

`provenance()` в `src/common.py` считает `data_train_sha256` и
`data_val_sha256` честно — их выбрасывал вызывающий код.

**Как проявлялся.** Замер на сломанной версии:

```
data_train_sha256: ОТСУТСТВУЕТ
data_val_sha256:   ОТСУТСТВУЕТ
```

Код, конфиг и ревизия базовой модели закреплены, а данные — нет. Run,
обученный на другом train/val, внешне неотличим от правильного, и сравнение
шести конфигураций молча перестаёт быть сравнением: достаточно перезаписать
`data/tokenized/train.pt` между запусками.

**Как исправлен.** Фильтр убран, в теги уходит полный provenance:

```python
versions = provenance(p)
```

**Каким числом подтверждается.** У всех шести runs присутствуют оба тега,
`data_train_sha256 = aa6aadf20248…`, `data_val_sha256 = ef61b003adba…`,
и они совпадают с текущим состоянием файлов. Проверка 2 сверяет четыре ключа
(`code_sha256`, `config_sha256`, `data_train_sha256`, `data_val_sha256`) с
пересчитанным provenance и проходит; `src/promote.py::select` на расхождении
любого из них отказывается выбирать кандидата.

## Дефект 4 — порог по loss считался, но не применялся

**В чём был.** В `src/promote.py` функция `promote()` вычисляла отношение и тут
же регистрировала версию, не сравнивая его с порогом:

```python
ratio = run.data.metrics["final_val_loss"] / run.data.metrics["base_val_loss"]  # TODO: достаточно ли этого?
version = mlflow.register_model(f"runs:/{run.info.run_id}/model", name)
...
client.set_model_version_tag(name, version.version, "validation", "passed")
```

Готовая функция `gate()` с правильной проверкой лежала в том же файле и никем
не вызывалась. Тег `validation=passed` ставился безусловно — то есть порог
существовал только в виде записи в реестре.

**Как проявлялся.** Любой run регистрировался и получал alias, включая тот,
у которого loss после обучения хуже, чем до. Запись в реестре при этом
утверждала обратное.

**Как исправлен.** Порог проверяется до обращения к реестру:

```python
ratio = gate(run, threshold)
version = mlflow.register_model(...)
```

`gate()` бросает `ValueError`, и до `register_model` выполнение не доходит —
в реестре не появляется ни версии, ни alias, ни тега.

**Каким числом подтверждается.** Проверка 6 в `make check` пытается
зарегистрировать лучший run с порогом `max_val_ratio = 0.0`; фактическое
отношение лучшего кандидата — **0.8909**, порог не пройден, регистрация
отклонена, временная модель в реестре не создаётся. Проверка печатает
«PASS 6. Запрет регистрации при непройденном пороге».

При штатном пороге 1.0 тот же механизм пропускает кандидата: `all-r8-high`
с отношением 0.8909 зарегистрирован как версия 1 с alias `candidate`.

## Два дефекта окружения, не входившие в задание

Отмечаю их здесь, потому что оба относятся к тому же классу «команда
отработала и отрапортовала об успехе, не сделав ничего».

**Прокси перехватывал localhost.** В системе заданы `HTTP_PROXY` и
`HTTPS_PROXY` на `127.0.0.1:10809`, а `no_proxy` пуст, поэтому `requests`
тянул через прокси даже обращения к `127.0.0.1:5006`. Под нагрузкой тот отвечал
503, и первый sweep упал через 4 минуты на `connect()`. В `Makefile` добавлен
экспорт `NO_PROXY`/`no_proxy` для локальных адресов.

**DVC не видел собственные стадии.** Первая версия `.gitignore` исключала
`data/` целиком и возвращала обратно только `*.dvc`. Git такой паттерн
понимает, обход DVC — нет: он не спускается в исключённый каталог. `dvc push`
и `dvc pull` отвечали «Everything is up to date», не перенеся ни байта, и
удалённое хранилище оставалось пустым при нулевом коде возврата. Поймано
клонированием репозитория во временный каталог и попыткой восстановить данные
с нуля. Правила переписаны так, чтобы `data/eval` не исключался на уровне
каталога; после этого свежий клон восстанавливает все три файла, md5
`15b44d90226076a4e3b9053c721720e9` для `golden.jsonl` совпадает с указателем.
